## Diagnosis (2026-01-22)

**Summary:** `Atomics.waitAsync` for BigInt arrays returns a nullish/stub result in agent runs, so `.value` access throws before assertions; async wait/notify semantics are not implemented.

**Error Pattern:**
```
Asynkron.JsEngine.ThrowSignal: Unhandled JavaScript throw: 'TypeError': 'Cannot read properties of null or undefined'
```

**Analysis:**
All failures abort with a `TypeError` while evaluating `Atomics.waitAsync(...).value` (often inside `$262.agent` scripts). That implies the `Atomics.waitAsync` call is producing a null/undefined result in these scenarios, so property access fails before any spec assertions run. The current implementation is a synchronous stub that never creates a waiter list or a Promise-backed `WaitAsyncResult`, and `Atomics.notify` never wakes waiters. Test262’s BigInt waitAsync tests rely on proper async wait/notify behavior across agents; the stubbed implementation cannot satisfy those expectations.

**Fix Direction:**
Implement full `Atomics.waitAsync`/`notify` semantics for `SharedArrayBuffer` + `BigInt64Array`: return `{ async: true, value: Promise }` when a wait is possible, `{ async: false, value: "not-equal" }` when the value mismatches, and resolve the Promise with `"ok"` or `"timed-out"` on notify/timeout. Maintain a per-buffer/index waiter list, wire it into the `$262.agent` harness, and ensure BigInt conversions and index validation follow the spec.
